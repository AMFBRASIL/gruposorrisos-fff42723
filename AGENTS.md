# Project rules
- Order approval workflows use immutable per-order template snapshots and pure sequential assignee checks in order-workflow.ts; store actions gate final approval and stock reservation so configuration cannot bypass operational inventory rules.
- Supplier registration and purchasing share the purchasing.ts in-memory supplier list; the registration route is distinct from supplier orders to keep master data and transactions separate.
- Supplier summary derives scoped request and confirmed purchase counts without double-counting converted requests; portal access fields are presentation-only demo settings, never real credentials.
- DialogContent owns the shared modal frame and overlay; custom wizard layouts retain their contents while global frame constraints normalize scrolling and dimensions, and simple dialogs receive a shared image rail without artificial steps.
- Branch and ERP-user forms use WizardShell with staged fields and final review; presentation changes preserve existing store permissions and save rules.
- MovementReview derives pre/post quantities and stock valuations from the live stock snapshot without mutating inventory; quantities are grouped by unit to avoid adding incompatible volumes.
- CSV parsing uses PapaParse with explicit column mapping and pure reconciliation in order-csv.ts; ambiguous names require human confirmation to prevent catalog substitutions.
- Supplier requests and versioned prices live in supplier-orders.ts, separate from CD orders; approval creates one purchasing record and never changes stock before receiving.
- Client and supplier portals share the in-memory supplier portal adapter and price wizard; access is simulated and responses reuse the demo purchasing store, with no Cloud calls or persistence.
- Current Start bundler options are mirrored into Vite 7 rollupOptions by a compatibility plugin because generated client entries otherwise fall back to index.html.
- Monetary form controls use CurrencyInput backed by react-number-format; callbacks retain numeric amounts so masks cannot corrupt calculations or saved values.
- ERP domain rules (orders state machine, branch access `can`/`visibleBranchIds`) live as pure functions in src/lib/orders.ts and src/lib/erp.ts, tested in src/lib/*.test.ts; UI calls store wrappers only — so rules can move to a real backend later.
- Demo data is in-memory (src/lib/stock.ts, erp.ts, orders.ts, purchasing.ts); only the simulated user and branch filter persist in localStorage.
- Stock intelligence rules are pure functions in stock-intelligence.ts; stock-advanced.ts owns demo orchestration and enforces branch permissions, independent adjustment review and stale-count checks so UI cannot bypass these rules.
- Camera scanning dynamically imports @zxing/browser after user action and stops streams on close; shared scanner accepts keyboard readers and manual codes when a camera is unavailable.
- Development builds use scripts/build-development.mjs to pin vite.config.ts; preview-injected SPA configs must not replace TanStack Start's generated client/server entries.
